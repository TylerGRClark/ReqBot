# WP-45.10 addendum — the Docling upgrade comparison and the registered rules for the measurements (written before any measure was read)

*Follows [PHASE45_WP4510_PLAN.md](PHASE45_WP4510_PLAN.md) (#245). The owner said (2026-10-07) that local model time is free and that updating Docling is a good idea. Conversions had been started (raw data, nothing analysed) when this was written; no measure below had been computed.*

## 1. The upgrade comparison

- **Candidates.** The pinned release `docling==2.94.0` (with `docling-core` 2.99.0, `docling-parse` 5.7.0, `docling-ibm-models` 3.13.0) against `docling==2.135.0`, installed in a separate virtual environment (`~/wp45_10_venv`, system site-packages shared so the repository's own install is untouched). Each release converts the same 13 pinned PDFs (hashes verified) with `DocumentConverter()` as production calls it, and chunks through the unmodified production function `pipeline.chunk_text.run_structure_aware` with that release's own default `HybridChunker()`. The cached conversions and chunk files live under `~/reqbot-work/scratch/wp45_10_cache/<release>/` outside the repository.
- **Measures (all offline, no LLM).** (1) Text items present in one conversion and absent from the other, counted and listed; (2) tables: count, how many have a different cell grid, the header-caption defect in `afi17-203` Table 3.2 and the number of table-labeled regions with no grid; (3) the labeled lead-in co-location rate and the word 6-gram text preservation of the emitted chunk records, as defined in `analyze_chunks.py` and the plan; (4) the number of chunks, their size distribution and conversion time per document; (5) heading levels against the numbering-based depth.
- **Decision rule for "recommend the upgrade", fixed now:** all of (a) every text item the 2.94.0 conversion has is present in 2.135.0 or each missing one is listed and read, and no more than 0.5% of text items are lost without an explanation read by me; (b) no table-defect measure worse (caption-in-header tables not more, no-grid regions not more); (c) the lead-in co-location rate not lower; (d) the emitted chunk records' 6-gram loss against 2.94.0 not above 1%, every difference listed; (e) all 13 conversions succeed; (f) the repository's own tests pass on 2.135.0 in the separate environment. Failing any one means *not recommended as is*, with the reason; passing all means *worth a pilot*, which is a separate pull request that moves the pin, re-runs the tests and replays ingestion on the pinned documents. The comparison cannot say the new release extracts *better requirements*; only a Step C pilot can.

## 2. Registered rules for the option and chunk-limit measurements (the plan's section 3, made exact)

- **H1.** Limits 256 (explicit, with the control that it is record-identical to `HybridChunker()`'s default), 512, 1,024, 2,048 and 4,096, default tokenizer, production function. *Worth a pilot* if the co-location rate rises by at least 5 percentage points over the 256-token baseline, the emitted-text 6-gram loss against the 256 baseline is at most 0.5% with every difference listed, no chunk leaves less than a 1,000-token answer allowance in Step C's 8,192-token window after the fixed prompt (repository token estimate), and the lead-in co-location of quotes found is computed on at least 100 labeled items. The smallest limit that passes is the candidate.
- **H2 (descriptive only).** `do_ocr=False`, `force_full_page_ocr=True`, `force_backend_text=True`: text items lost and extra against the baseline, listed. No pilot is proposed from H2.
- **H3.** `do_cell_matching=False` and `TableFormerMode.FAST`: tables with a different grid; the known cases. *Worth a pilot* if the caption-in-header tables or the no-grid regions fall and no text item is lost.
- **H4.** Docling's heading level against `_estimate_heading_depth` on the baseline conversions: disagreement counts and examples. Descriptive; any use of the level is a separate plan.
- **Reading the results.** A pass of a rule is *worth a pilot*, nothing more. Changing the chunk limit changes every chunk id and forces Step C re-extraction and a reindex (the plan's section 5).
