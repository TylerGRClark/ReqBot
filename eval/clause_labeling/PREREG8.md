## Q1. Should the labeler get the lead-in that `pipeline/lead_in.find_lead_in` finds?
Today the labeler is shown `ctx_lead` (pipeline/clauses.py): the nearest preceding clause in the same chunk whose text ends in a colon; it never expires and never crosses a chunk. The checklist uses `find_lead_in` (sibling logic, looks back one chunk if that chunk is in the same section).
- **control** = current code, unchanged.
- **rule** = identical in every respect (frozen prompt v3 text and sha, model, temperature 0, batch size 4, num_ctx 8192, num_predict 300, clause cuts, batch composition) except that each clause's `ctx_lead` field is replaced by `find_lead_in(raw_text, clause.start, previous chunk's raw_text if it is in the same section else "")`, or none when that returns None. `clause_block` renders it unchanged as `Lead-in line above: <text[:300]>` inside `Context:`. Note what this changes: (a) the text is the lead-in's last sentence without its list marker, not the full clause text with marker; (b) plain sentences get no lead-in; (c) a clause that is itself a list item may get its parent lead-in (control gives a lead-in clause none); (d) table grid lines get whatever find_lead-in returns (expected none).
- **control2** = a second run of control, to measure the noise floor (temperature 0 is not always bit-exact on this server).

Whole documents are relabeled in every arm (batch composition identical between control and rule, only the context text differs), so no old labels are reused.

## Q2. Speed settings
Separate arms, each = control with ONE change, same documents: **b8** (batch size 8), **b16** (batch size 16), **c4096** (num_ctx 4096), **p100** (num_predict 100). Then **combo** = all of those settings that individually met the quality rule Q2-a..c (below), whatever their speed. The prompt template and its sha are untouched in all arms (a batch is simply more `[n]` blocks).

## Metrics (scoring setup of PREREG6/7: the same `match`/`squash` rules, the silver 0.8 agreement rule and gold2 `gold_both`)
A clause is a row when its label is not NOT_REQUIREMENT (UNSURE counts as a row, as in production). Rows are scored against the gold units of the document by the PREREG7 `quality` function: **recall** = gold requirements covered by a row inside their unit / gold requirements; **precision** = rows inside gold units that match a gold requirement / rows inside gold units. Pooled over the seven documents. Gold truth is two model families agreeing (plus owner rulings on gold2), so precision is a lower bound.
- Q1 extras: (1) **flips** control vs rule on clauses whose context changed: a list of every clause whose requirement-ness (row vs NOT_REQUIREMENT) changed, printed with old and new context, the label and whether it lies in a gold unit; (2) a flip inside a gold unit is **judged by gold**: new label row and the clause matches a gold requirement = correct; new label row and no match = wrong; new NOT_REQUIREMENT and the clause matches a gold requirement = wrong; new NOT_REQUIREMENT and no match = correct. Flips outside gold units are listed but not scored (the author may comment, marked as not blind); (3) the same recall/precision computed only over **list-item clauses** (`fragmentation.is_list_item`) in gold units, descriptive; (4) label agreement between arms over all clauses and over changed clauses only.
- Q2: per-clause label agreement with control (and control2 vs control as the floor), recall/precision, parse failures (batches that ended UNSURE for lack of a parsable answer), failed batches, wall seconds (sum over documents of the labeling loop only, model load excluded by a warm-up call before the first timed batch of each run).

## Pass rules (fixed now)
Noise floor N = max(1.0, |recall control2 - recall control|, |precision control2 - precision control|) in points; reported.
- **Q1 passes if all of:** (Q1-a) recall(rule) >= recall(control) - 1.0; (Q1-b) precision(rule) >= precision(control) - 1.0; (Q1-c) among gold-judged flips, correct > wrong (strictly). If fewer than 6 flips fall inside gold units, Q1-c is reported as "too thin" and Q1 is NOT called a pass (no evidence of benefit); the flips list still goes to Tyler as information.
- **Q2 per setting, quality rule:** (Q2-a) recall >= control - N; (Q2-b) precision >= control - N; (Q2-c) unparsed batches <= control's + 1 per 100 batches and failed batches 0. **Speed rule:** (Q2-d) label seconds <= control seconds / 1.5 (control seconds = mean of control and control2). **Q2 passes for a setting** when a-d all hold; the prompt sha must be unchanged (checked in the ledger). The combination arm is judged by the same rule and is the headline when no single setting reaches 1.5x. Per-clause agreement with control is reported but is not a pass criterion beyond a-c (agreement below control2-vs-control is called out).
- Verdict wording: PASS / FAIL / THIN (not enough evidence). No rule is changed after the run.

## Resume-ledger note (to be verified in code and stated in the report)
`input_hash = sha256(model + "\n" + filled prompt)`, and the ledger key is (clause_keys, input_hash). The context text and the batch composition are inside the filled prompt, so a new lead-in rule or batch size makes old ledger records unmatchable: they are not reused (safe, they are recompacted away at the end of a run). `num_ctx` and `num_predict` are NOT in the hash: after changing them an old ledger is silently reused for batches whose prompt is unchanged. That is harmless at temperature 0 only if the old and new settings give the same labels, which this experiment measures.

## What a pass does and does not mean
A pass means the change did not measurably hurt on seven documents; it changes no behaviour here. Adoption of a changed context needs Tyler's decision (it changes what the labeler sees and forces a library re-run; the frozen prompt text and sha stay the same, only the context field differs). Speed settings would not change labels' meaning but do change the ledger hash for batch size.

## Limits stated in advance
Seven documents, one model, one prompt, one run per arm plus one repeat of control. Truth is two model families, not a human audit; only sampled paragraphs of each document carry gold, so most flips cannot be judged against gold. About 17% of clauses change context, so gold units hold few changed clauses: Q1-c may come out THIN. Timing is wall clock on a shared network server (nothing else of mine running; other users unknown). The author (not a blind reviewer) reads the flips list and says so.
